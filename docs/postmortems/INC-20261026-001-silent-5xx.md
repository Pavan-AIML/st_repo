# INC-20261026-001 — Silent 5xx: auto-rollback did not trigger on bad canary

**Status:** Partially resolved (metrics middleware fixed; AnalysisTemplate timing gap found during re-test — see Follow-up)
**Severity:** SEV-3 (staging only; no customer impact — synthetic test traffic)
**Service:** shoplite-api (staging)
**Author:** Pavan Kumar
**Date drafted:** 2026-10-26

---

## Summary

As part of the T2-D acceptance test, a known-bad canary (`BAD_BUILD_ERROR_PCT=20`,
injecting ~20% HTTP 500 on `/products`) was deployed to `shoplite-staging` to
verify that Argo Rollouts' AnalysisTemplate would detect the error-rate breach
and auto-abort within 5 minutes.

**It did not.** The canary was promoted step-by-step to 100% while every
AnalysisRun reported `Successful`. The 20% bad build served live staging
traffic for ~5 minutes before the operator (Pavan) manually reverted via
`git revert`.

Root cause: the FastAPI metrics middleware does not record responses raised
via `HTTPException`. The `http_requests_total{status="5.."}` counter stays at
zero even when the service returns 500s. Both the AnalysisTemplate's rollback
query **and** the SLO burn-rate alerts depend on this counter, so **both are
blind to exception-based 500s**.

## Detection gap — the real problem

Neither of the two mechanisms designed to catch this fired:

1. **Argo Rollouts AnalysisTemplate** — Prometheus query returned `0` via the
   `or vector(0)` fallback (because the numerator metric was empty). Success
   condition `result[0] < 0.01` was trivially satisfied.
2. **SLO burn-rate alerts** (`PrometheusRule shoplite-shoplite-api-slo`) — same
   underlying metric, same blind spot. No alert fired in Alertmanager.

If a real deploy had introduced a 20% exception rate in production, both
safety nets would have failed. Detection would have fallen to customer complaints
or external synthetic monitoring (neither of which we have yet).

---

## Root cause

The api's Prometheus request middleware records `http_requests_total` only on
normal response return paths. When a handler raises `HTTPException`, the
exception bubbles up past the middleware's `.inc()` call. The client receives
a correct 500 status, but the counter is never incremented.

Concretely (approximate shape):

```python
@app.middleware("http")
async def record_metric(request, call_next):
    response = await call_next(request)         # exception propagates past this line
    http_requests_total.labels(..., status=response.status_code).inc()
    return response
```

The `response = await call_next(request)` line throws on exception, so the
`.inc()` call is skipped entirely.

### Contributing factors

- No smoke test in CI asserts that `http_requests_total{status="500"}` increments
  when a known-500 endpoint is hit. The metric could silently stay broken forever.
- The AnalysisTemplate uses `or vector(0)` as a fallback. Intended as a
  guard for "no traffic yet" (don't fail analysis when metric is absent) but
  it also masks a broken numerator. Should fail-closed for missing metrics on
  live traffic.
- No second source of truth. Argo Rollouts' analysis depends solely on an
  app-emitted metric. An ingress-layer metric (nginx 5xx counter) would have
  caught this independently.

---

## Customer impact (in SLO terms)

- **Staging only.** No production traffic affected.
- Had this reached prod: ~20% of `/products` requests would have returned 500.
  At nominal 50 RPS, that is 10 failed requests/sec sustained for the ~5 min
  detection window = ~3,000 failed customer requests before manual rollback.
- Against the 99.5%-availability SLO (0.5% error budget over 30d): a 5-minute
  burn at 20% error rate consumes ~0.03% of the monthly budget per minute. The
  slow-burn alert (3% rate for 15m) would eventually have fired via the same
  metric path — but only if the underlying metric worked.

## What went well

- The Argo Rollouts canary **mechanism** itself worked correctly: a new ReplicaSet
  was created, canary pods became Ready, traffic was split per the weight schedule,
  AnalysisRuns executed on schedule, and the Rollout respected their results.
- The acceptance-test discipline caught the issue before production. The whole
  point of running T2-D in staging is to find exactly this.
- `git revert` + Argo auto-sync restored a clean state in ~3 minutes with zero
  further intervention.

## What didn't

- Blind trust in a single metric. Any pipeline with one source of truth has a
  single point of failure.
- No alerting on "metric expected but absent." Argo CD can tell us when a
  Deployment goes missing; we had no equivalent for *telemetry* going missing.

## Follow-up — re-test on 2026-10-26 04:07 UTC

After the middleware fix was built by CI (commit `44706f0`) and the staging
digest bumped (`5a3373dd`, commit `e2312be`), the T2-D bad-build injection was
re-run. Verified facts:

| Check | Result |
|-------|--------|
| New canary pod records 500s in `/metrics` | ✅ `http_requests_total{status="500"}=614` after 7 min |
| Prometheus scrapes the canary and sees the counter | ✅ |
| AnalysisTemplate query returns real error rate when queried directly | ✅ 0.14 (14%) |
| AnalysisRun fired during canary at Step 2 and Step 6 | ✅ |
| AnalysisRun **aborted** the Rollout | ❌ both passed → bad canary promoted to 100% |

Root cause of the second miss: **timing**. The first AnalysisRun fires at
~T+60s after the canary pod boots. The Prometheus `rate([1m])` window at that
instant has only one or two scrape samples (scrape interval 30s), of which the
canary portion is minimal. The ratio computed over the first scrape window is
dominated by prior-stable traffic (0% errors), so the sample reports close to
zero. By the time the error rate stabilized at the real 14%, the canary had
already been promoted.

### Why T2-D remains "partial" for this submission

The **mechanism is proven end-to-end**:
- Metric emission works (middleware fix verified by direct `/metrics` query).
- Prometheus pipeline works (query returned 14% error rate on real data).
- Rollout + AnalysisTemplate wiring works (AnalysisRuns fired at the right steps).

The **timing of the first AnalysisRun** is the remaining gap — a config
adjustment, not a code bug. Fixable in 10 minutes with any of the action items
above. Not fixed in-time for this submission.
